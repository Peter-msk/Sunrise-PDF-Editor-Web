## 적용과 검증 순서

1. 관리자 소스 차이를 정리하고 기능 검증을 시작한다. 이번 마무리 회차에는 문법 확인만 수행한다.
2. 기존 테스트 중 변경된 API 계약에 맞춰 수정할 항목을 확인하고 정상/실패/취소/권한/동시성 시나리오를 실행한다.
3. 브라우저와 Windows 실사용을 검증한다. 운영 배포 전에 미해결 결함을 수정한다.
4. 운영 백업과 격리 복원 점검 후 0005~0015 스키마를 순서대로 적용할 계획을 검토한다. 운영에 이미 직접 적용된 0004를 재실행하지 않는다. 자동 일괄 마이그레이션을 현재 배포 워크플로우에 넣지 않았다.
5. Worker와 GitHub production 환경에 필요한 비밀값을 설정하고, 검토된 main에서만 수동 배포한다. 소스 작성 중에는 이 단계를 실행하지 않았다.

## 실제 데이터의 한계

- 재방문은 같은 익명 탭의 이전 날짜 기록 추정이며 사람이 아니다. 새 계측의 과거 데이터는 소급 생성하지 않는다.
- 편집 세션 평균은 실제 활성시간이 기록된 탭·일자 기준이며 완료 세션 평균이 아니다.
- 다운로드 요청/바이트 생성과 디스크 저장 완료는 다르다. 파일명, 검색어, 입력 내용은 계측에 저장하지 않는다.
- 희소 도구의 미계측이나 네트워크 누락을 전체 기능의 성공으로 해석하지 않는다.
- D1 내보내기와 복원 도구, 배포 워크플로우는 실제로 실행한 적이 없다.

현재 source candidate는 사용자용 원문 직접 수정·보안삭제·암호화·전자서명·Word/Excel 변환의 신규 구현 완료를 포함하지 않는다. 전체 7단계 개발계획은 유지된다.
